# Handoff: 세션 인계

다음 세션의 나는 이 대화를 전혀 기억하지 못한다. 인계문은 **그 상태에서 5분 안에 작업을 다시 시작할 수 있게 하는 문서**다. 작업 일지나 회고가 아니다. 다음 세션이 알아야 하고 코드나 git 로그로는 알 수 없는 것만 적는다.

## 이 스킬이 다루는 세 가지 상황

1. **인계문 작성**: "핸드오프", "인계", "세션 정리", "컨텍스트 정리" 요청, 또는 컨텍스트가 거의 찼을 때
2. **스냅샷 정리**: precompact 훅이 남긴 자동 스냅샷을 사람이 읽을 인계문으로 정리
3. **이어서 작업**: 새 세션에서 "이어서 작업", "지난번 거 계속" 요청이 오면 인계문을 읽고 재개

## 파일 위치

- 인계문: `handoff/handoff.md` (항상 최신 하나만 유지)
- 지난 인계문: `handoff/archive/YYYY-MM-DD-HHMM.md`
- 자동 스냅샷: precompact 훅이 쓰는 경로 (기본 `handoff/snapshots/`). 훅 설정에 다른 경로가 있으면 그것을 따른다.

`handoff/`가 없으면 만든다. 인계문은 개인 작업 상태이므로 저장소에 커밋할지는 사용자에게 맡기고, 묻지 않았다면 `.gitignore` 추가 여부만 한 줄로 제안한다.

## 1. 인계문 작성 절차

1. 현재 상태를 확인한다:
   - `git status`, `git diff --stat`, 현재 브랜치, 마지막 커밋 몇 개
   - 이번 세션의 대화에서 나온 목표, 결정, 막힌 지점
   - 테스트·빌드를 돌렸다면 마지막 결과
2. 기존 `handoff/handoff.md`가 있으면 `handoff/archive/`로 옮긴다(파일명은 그 인계문의 작성 시각). 덮어쓰기 전에 옮기는 것을 잊지 않는다.
3. 아래 템플릿으로 새 `handoff/handoff.md`를 쓴다.
4. 이번 세션에 되돌리기 어려운 결정(아키텍처·의존성·API 계약)이 있었고 아직 changelog에 없다면, changelog 스킬로 기록할지 사용자에게 묻는다. 인계문에는 결정을 짧게만 적고 changelog 항목을 가리킨다.
5. 커밋되지 않은 변경이 있으면 인계문에 명시하고, 커밋할지 사용자에게 묻는다. 멋대로 커밋하지 않는다.
6. 사용자에게 인계문 경로와 "다음 할 일" 첫 항목을 알려 준다.

컨텍스트가 거의 찬 상황이면 1번 확인을 최소화하고 바로 쓴다. 완벽한 인계문보다 잘리지 않은 인계문이 낫다.

## 인계문 템플릿

```markdown
# Handoff — YYYY-MM-DD HH:MM

## 목표
이 작업이 최종적으로 달성하려는 것 1~2문장. 사용자가 원래 요청한 범위와 완료 기준.

## 현재 상태
- 브랜치: `<branch>` (마지막 커밋 `<short-sha>` <메시지>)
- 커밋 안 된 변경: 있음/없음 — 있으면 파일과 상태 한 줄씩
- 테스트/빌드: 마지막 실행 결과 (통과/실패, 실패면 무엇이)

## 완료한 것
- 무엇을 했는지, 결과로 무엇이 동작하는지. 파일 경로 포함.

## 진행 중인 것
- 중간에 멈춘 작업과 **어디까지 했는지**. 반쯤 고친 파일, 절반만 적용한 리팩터링 등.

## 결정한 것
- 결정과 이유 한 줄씩. 되돌리기 어려운 결정은 `changelog/changelog.md`의 해당 날짜 항목을 가리킨다.
- 사용자가 명시적으로 원하거나 원하지 않는다고 한 것(취향, 제약)도 여기에.

## 시도했지만 안 된 것
- 무엇을 시도했고 왜 안 됐는지. 다음 세션이 같은 길을 다시 가지 않도록.

## 막힌 것 / 열린 질문
- 사용자 답을 기다리는 질문, 외부 요인으로 막힌 것.

## 다음 할 일
1. 가장 먼저 할 일 — 구체적인 파일·명령 수준으로
2. ...

## 참고
- 핵심 파일 경로, 관련 이슈/PR, 유용했던 명령어
```

작성 원칙:
- **다음 할 일의 첫 항목은 바로 실행할 수 있어야 한다.** "인증 개선 계속"이 아니라 "`src/auth/session.ts`의 `refresh()`에 만료 체크 추가 후 `npm test auth` 실행".
- 해당 사항이 없는 섹션은 "없음"으로 적는다. 비어 있으면 빠뜨린 건지 없는 건지 모른다.
- 코드를 붙여 넣지 말고 파일 경로와 함수명으로 가리킨다. diff는 git에 있다.
- "시도했지만 안 된 것"은 가장 가치 있는 섹션이다. 대화가 사라지면 제일 먼저 잃는 정보다.
- 추측을 사실처럼 쓰지 않는다. 확인 안 한 것은 "(미확인)"을 붙인다.
- 전체가 한두 화면 안에 들어오게.

## 2. precompact 스냅샷 정리

precompact 훅은 컨텍스트 압축 직전 기계적 스냅샷(대화 요약, 변경 파일 목록, 도구 호출 기록 등)을 남긴다. 그대로는 읽기 어렵고 중요도 구분이 없다.

1. 스냅샷 경로에서 가장 최근 파일을 찾는다. 사용자가 특정 스냅샷을 지정하면 그것을 쓴다.
2. 스냅샷을 전부 읽는다. 이어지는 스냅샷이 여러 개면 기존 `handoff/handoff.md` 이후의 것을 모두 읽는다.
3. 현재 git 상태와 대조해 스냅샷 이후 바뀐 것을 확인한다. **스냅샷과 실제 상태가 다르면 실제 상태가 우선이다.**
4. 템플릿에 맞춰 옮기되:
   - 도구 호출 기록, 파일 읽기, 탐색 과정은 버린다.
   - 결정, 실패한 시도, 사용자가 말한 제약은 반드시 살린다.
   - 스냅샷에서 목표나 이유가 불분명하면 "(스냅샷에서 불분명)"으로 표시하고 지어내지 않는다.
5. 위 "인계문 작성 절차"의 2~6번을 따른다.
6. 정리가 끝난 스냅샷은 지우지 않는다. 삭제는 사용자가 결정한다.

## 3. 이어서 작업

새 세션에서 이어서 작업하라는 요청이 오면:

1. `handoff/handoff.md`를 읽는다. 없으면 가장 최근 스냅샷을 찾고, 둘 다 없으면 그렇다고 말하고 무엇을 이어갈지 묻는다.
2. 인계문 시각 이후의 변화를 확인한다: `git log`, `git status`. 인계 이후 누군가(사용자 포함) 작업했을 수 있다.
3. 사용자에게 3~5줄로 요약한다: 목표, 현재 상태, 다음 할 일 첫 항목, 열린 질문. 인계문과 실제 상태가 어긋나면 그것도 알린다.
4. 열린 질문이 다음 할 일을 막고 있으면 먼저 묻는다. 막지 않으면 바로 다음 할 일 첫 항목부터 시작한다.
5. 작업하면서 인계문을 수정하지 않는다. 세션이 끝날 때 새 인계문을 쓴다.
