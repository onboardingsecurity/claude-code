# Changelog: 되돌릴 수 없는 결정 기록

이 스킬의 목적은 "무엇을 바꿨나"가 아니라 **"왜 그렇게 결정했나"**를 남기는 것이다. 커밋 로그와 diff는 변경 내용을 이미 보여 주므로, 여기에는 나중에 코드만 봐서는 알 수 없는 맥락(당시의 제약, 버린 대안, 감수한 비용)을 적는다.

## 언제 기록하나

기록 대상 (하나라도 해당하면 기록):
- **아키텍처**: 모듈 경계·레이어 구조 변경, 저장소/DB/큐 등 인프라 선택, 동기↔비동기 전환, 모노레포 분리·통합
- **의존성**: 새 런타임 의존성 추가, 핵심 라이브러리 교체, 메이저 버전 업그레이드, 의존성 제거, 런타임/언어 버전 변경
- **API 계약**: 공개 엔드포인트·스키마·이벤트 포맷·CLI 인터페이스의 추가/변경/폐기, 하위 호환을 깨는 변경, 인증 방식 변경

기록하지 않는 것:
- 패치/마이너 버전 자동 업데이트(보안 패치 포함), lockfile만 바뀐 경우
- devDependency 중 빌드 결과나 개발 흐름에 영향 없는 도구 추가
- 내부 리팩터링, 버그 수정, 스타일 변경
- 이미 기록된 결정을 그대로 이행하는 후속 작업

애매하면 스스로 묻는다: **"6개월 뒤 누군가 이걸 되돌리려 할 때, 이유를 모르면 곤란한가?"** 그렇다면 기록한다.

## 기록 절차

1. `changelog/changelog.md`가 있는지 확인한다. 없으면 아래 "파일 헤더"로 새로 만든다.
2. 기존 항목을 훑어 같은 주제의 이전 결정이 있는지 확인한다.
3. 결정의 근거를 모으는 순서:
   - 대화에서 사용자가 말한 이유
   - 관련 diff, 커밋 메시지, PR 설명, 이슈
   - 그래도 **근거가 불분명하면 추측으로 채우지 말고 사용자에게 묻는다.** 근거 없는 항목은 기록하지 않는 것만 못하다.
4. 아래 템플릿으로 **파일 맨 끝에** 항목을 추가한다(오래된 것이 위, 최신이 아래).
5. 추가한 항목을 사용자에게 보여 주고, 필요하면 같은 커밋에 포함하도록 안내한다.

## 항목 템플릿

```markdown
## YYYY-MM-DD — <결정을 한 줄로: 동사로 시작>

- **분류**: 아키텍처 | 의존성 | API 계약
- **결정**: 무엇을 하기로 했는지 1~2문장.
- **배경**: 이 결정이 필요해진 상황·문제·제약.
- **근거**: 왜 이 선택인지. 측정값, 벤치마크, 링크가 있으면 포함.
- **검토한 대안**: 고려했지만 버린 선택지와 버린 이유(한 줄씩).
- **영향**: 바뀌는 코드 범위, 마이그레이션 필요 여부, 호환성 파괴 여부, 영향받는 사용자·서비스.
- **되돌리는 비용**: 되돌리려면 무엇이 필요한지, 왜 어려운지.
- **참고**: PR/이슈/커밋 링크 (없으면 생략)
```

작성 원칙:
- 날짜는 결정이 확정(머지·push)된 날 기준, ISO 형식.
- 제목은 "~로 전환", "~ 도입", "~ 폐기"처럼 결과가 드러나게.
- 해당 사항이 없는 필드는 "없음"으로 적고 빼지 않는다. 특히 "검토한 대안: 없음"은 그 자체로 의미 있는 정보다.
- 간결하게. 한 항목이 화면 한 페이지를 넘지 않게.

## 과거 항목은 수정하지 않는다

이 파일은 추가 전용(append-only)이다. 이전 결정이 뒤집히거나 바뀌면 기존 항목을 고치지 말고 새 항목을 추가한 뒤, 새 항목에 `- **대체**: YYYY-MM-DD <이전 제목>` 한 줄을 넣는다. 기존 항목에는 제목 옆에 `(→ YYYY-MM-DD에 대체됨)` 표시만 덧붙이는 것을 허용한다. 오타·깨진 링크 수정은 예외다.

## changelog-reminder 훅으로 호출된 경우

push나 PR 생성 직전 훅이 매니페스트(package.json, pyproject.toml, go.mod, Cargo.toml, requirements*.txt, Gemfile, pom.xml, build.gradle 등) 변경을 감지해 알리면:

1. 훅이 알려 준 파일의 diff를 base 브랜치(또는 마지막 push 지점) 기준으로 확인한다.
2. 변경을 분류한다:
   - lockfile만, 또는 패치/마이너 업데이트만 → 기록 불필요. "기록할 결정 없음"과 이유를 한 줄로 알리고 끝낸다.
   - 새 런타임 의존성, 교체, 제거, 메이저 업그레이드, 엔진/런타임 버전 변경 → 기록 후보.
3. 기록 후보가 있으면 무엇을 기록할지 요약해 사용자에게 확인받는다. 근거를 대화·커밋에서 찾을 수 없으면 이때 함께 묻는다.
4. 확인되면 위 절차대로 기록한다. 사용자가 건너뛰기로 하면 강요하지 않는다.
5. 매니페스트 변경이 없어도, 같은 push에 API 스키마(OpenAPI, GraphQL, protobuf 등)나 아키텍처 변경이 보이면 함께 검토를 제안한다.

훅은 알림만 할 뿐 push를 막는 용도가 아니다. 검토는 빠르게 끝낸다.

## 파일 헤더 (파일이 없을 때)

```markdown
# Changelog

되돌리기 어려운 결정과 그 근거를 시간순으로 기록한다. 최신 항목이 아래에 온다.
과거 항목은 수정하지 않고, 결정이 바뀌면 새 항목으로 대체한다.
```
